# 管理员二次确认与 MCP 写入

## 已实现的审批链路

1. 指定飞书管理员在白名单群 @机器人发送 `确认告警 123456`。
2. 机器人生成随机审批号，保存请求者真实 `open_id`、群 ID、事件 ID 和五分钟有效期。
3. **同一管理员** @机器人发送 `确认执行 <审批号>` 或 `取消执行 <审批号>`。
4. 服务端再次验证管理员、群 ID、审批有效期，并通过 Redis 原子状态更改阻止重复确认。
5. 默认 **dry-run**：只提示模拟执行成功，不实际修改 Zabbix。
6. 只有运维人员显式启用后，才把固定白名单操作排入独立 `ai-changes` Worker。

## 安全边界

- 仅支持 `event_acknowledge`（确认事件），不允许 AI 自由选择其他工具名或参数。
- MCP 写入实例必须独立部署，使用独立的最低权限 Zabbix API Token。
- 独立 Worker 环境变量 `ZABBIX_WRITE_MCP_URL`、`ZABBIX_WRITE_MCP_TOKEN` 不共享给问答、告警及 Web 服务。
- `AI_WRITE_ENABLED` 默认关闭，仅当服务器环境变量显式设置为 `true` 时启用；Web 无权开启。
- 同一审批只允许尝试一次。MCP 结果不明确时标为 `uncertain`，不自动重复写入。
- MCP 写入工具参数目前按常见 initMAX Zabbix MCP 接口设计，**须在测试 Zabbix 上验证工具模式后才能在生产启用**。
- 变更完成回查及飞书结果回填尚未联调；不要将它视为完整的生产变更管理系统。

## 飞书示例

```text
@AI 确认告警 123456
@AI 确认执行 a1b2c3d4e5f6
```

管理员 Open ID 配置在 Web 的 `ai_approver_open_ids`。

## 飞书引用告警

对告警卡片点击“回复”，输入 `@AI 帮我分析这个告警`。机器人读取回复消息的 `parent_id`，获取原卡片内容并提取事件 ID，然后经 MCP 核验。企业应用需有访问群内被回复消息的权限；由自定义 Webhook 发送的原卡片，须经实际权限测试。
